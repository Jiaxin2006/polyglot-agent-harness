# Report Generator（结构化报告技能）

## 何时必须调用

满足任一条件就必须调用本技能，并把结果落到本地报告文件中（默认不提交到上游 PR）：

- **运行出现问题**：任何阻塞性的 build/link/run/test 失败（要记录现象与复现）
- **发现或修复 bug**：能用日志/测试证明（要记录证据链与验证）
- **CI 变红/代码跑不过**：即使问题最终被证明是资源/环境（例如磁盘不足），也必须在报告中记录“现象→定位→处置→结果”，并给出对应 PR/commit
- 改动了构建链路/开关语义（例如 feature / env / toolchain flags）
- 新增/修复了一个可跑通的端到端/CI 用例（要记录通过证据）
- 准备交付：对齐上游、拆分 PR、准备提交信息与验证证据

## 输出落点（本地）

在目标项目工作区创建/更新以下文件（不存在则新增）。要求：**报告必须存在**，但默认只作为本地/个人 fork 产物，**不要提交到上游 PR**：

- 推荐落点（二选一）：
  - **未追踪文件**：在仓库内 `reports/` 下维护，但始终保持 untracked（或只进个人 fork 分支）
  - **仓库外本地目录**：放到 `<repo>/../reports-local/<repo-name>/...` 之类的位置，避免误提交

文件建议：

- `<...>/<topic>-report.md`：对外可读的主报告
- `<...>/<topic>-journal.md`：按时间追加的工作日志（可选，但建议保留）

`<topic>` 建议使用短横线格式，例如：`backtrace-issue-146`、`postgresql-16.4`。

## 报告模板（参考 StarryOS/PostgreSQL 报告风格）

将下列模板复制到 `reports/<topic>-report.md`，并按本次工作填充；不要保留空洞占位：

### 1) 概述（TL;DR）

- 一句话结论（是否跑通/修复了什么/带来的能力）
- 关键事实：分支、平台、关键配置（例如 QEMU 机型、内存、是否动态链接/是否 DWARF）
- 可复现入口：最短命令或链接（如有外部复现仓库则贴）

### 2) 环境与复现步骤

- 代码基线：上游分支/commit，本地分支/commit
- 构建环境：Docker/DevContainer 镜像/工具链版本（如 rust-toolchain）
- 运行环境：QEMU 参数、内存、平台配置文件、关键 env
- 复现步骤：可复制命令（build + run/test + 日志收集）

### 3) 发现的问题（具体现象）

按条列出，每条包含：

- 现象（错误信息/日志片段）
- 影响（为什么会阻塞目标）
- 触发条件（何时发生）

### 4) 分析与思考（根因）

要求写出“证据链”：

- 初始假设 → 如何验证/证伪
- 追踪手段（日志/寄存器/内存/断言/二分）
- 根因（必须能解释现象）

如果是跨架构差异，必须明确指出差异来源（例如参数寄存器与返回值寄存器复用）。

### 5) 修复内容（按 PR 拆分）

每个 PR 一段，格式固定：

- PR 标题：（英文，祈使句；报告内可记录，**上游 PR 正文勿引用内部计划编号**如 `PR-1`、`TODO-2`）
- PR 草稿落点：`操作系统/pr-drafts/<repo-or-feature>-pr-draft.md`（**仓库外**，勿放入 `tgoskits/` 等 git 目录）
- 动机（为什么需要）：
- 实现要点（可读要点列表，不贴大段代码）：
- 影响面与风险：
- 验证（必须可复现）：

**Backtrace (#146) PR 草稿** — 正文首行必须为：`Tracking issue: https://github.com/rcore-os/tgoskits/issues/146`

### 6) 调试过程（可选但强烈建议）

当问题复杂或老师/评审可能追问时，按时间线写：

- 关键转折点（某个假设被证伪、某个 trace 给出证据）
- 关键观测（寄存器/内存/系统调用参数变化）

### 7) 测试结果（硬证据）

- E2E/CI 用例列表与通过情况（x/y）
- 关键日志片段（要能说明“真的跑通了”）
- 若涉及 backtrace：至少展示两帧 `BT` 行与 ip 非 0；如做 host symbolize，贴符号化结果片段

### 8) 已知限制与 TODO

- 当前缺陷/限制
- 下一步计划（按可提交的最小增量拆分）

## 执行步骤（本技能的工作流）

1. 确认本次 `<topic>` 与报告路径（默认 `reports/<topic>-report.md`）。
2. 收集事实：基线 commit、运行参数、失败/成功日志片段、测试命令、对应 PR/CI 链接（如有）。
3. 生成报告草稿（按模板填满，不留空）。
4. 如果本次是“新 E2E 跑通”：在报告里新增“测试结果”与可复现命令，并把日志证据保留到 `reports/<topic>-journal.md`（或主报告附录）。
5. 如果本次涉及 PR：按 PR 拆分列出并写明验证证据；PR 草稿写入 `操作系统/pr-drafts/`（见 §5），上游正文不含内部计划编号；Backtrace 工作引用 Issue #146 tracking line。
6. 如果本次是“运行失败/发现 bug”：必须补齐“现象→根因→修复/绕过→验证/回归”的闭环，并标明后续是否需要单独 PR。

## CI 失败条目（强制最小字段）

当触发原因是 “CI 变红/测试跑不过” 时，报告中必须至少包含：

- 失败用例/任务名（例如 `starry qemu findutils`、`fmt`）
- 关键错误片段（1–5 行，避免整段粘贴）
- 判断：代码 bug / 环境/资源 / flake（以及证据）
- 处置：做了哪些修改（文件/思路即可）与对应 commit
- 结果：哪条验证命令/哪条 CI 重跑能证明问题已缓解

**rustfmt / `fmt` job 失败** — 必须记录：`cargo fmt --all -- --check` 的非零退出、涉及的 `Diff in ...` 路径、本地 `cargo fmt --all` 后是否通过 re-check。常见 gotcha：`axbuild` 中 `let` chain 被 rustfmt 折叠为单行 `if cond && let Some(x) = y {`（见 `scripts/axbuild/src/arceos/test.rs`）。

## 常见教训（必须记录到报告）

- 如果修复触及 panic/oops/trap 路径：必须在报告中说明是否保留了递归/并发保护（例如 `enter_panic`/`enter_oops`/`oops_in_progress`/backtrace one-shot gate），避免引入“二次故障”。

## 质量门槛（必须满足）

- 报告必须能“离线阅读后复现”：至少一套 build + run/test 命令
- 报告必须能“回答追问”：现象、根因、修复点、验证证据四者闭环
- 不得使用机器路径作为唯一信息来源：用相对路径/仓库路径/配置文件名
